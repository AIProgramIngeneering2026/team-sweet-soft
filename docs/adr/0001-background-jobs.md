# ADR-0001. Фоновый запуск Job

Дата: 2026-11-14
Статус: предложено

## Контекст и ограничения

- Job выполняется долго. `series_summary` разбирает до 200 реплеев. `arena_sync` при недоступной AI Arena делает 3 попытки с таймаутом 10 с, то есть ждет больше 30 с. `local_match` играет матчи минутами.
- В жизненном цикле уже есть состояние `queued` и отмена в `running` ([requirements.md](../requirements.md#жизненный-цикл-job)). Чтобы они имели смысл, Job должен выполняться отдельно от запроса, который его создал.
- Клиент не должен держать соединение до конца работы. Если его оборвет таймаут клиента или прокси, клиент не узнает, создан ли Job (карта К2).
- Система это один сервис и PostgreSQL в Docker Compose ([README](../../README.md)). Брокеры сообщений в курсе не оцениваются, а каждый новый сервис усложняет запуск из чистого клона.
- Ядро (сервис Job, Dispatcher, Registry, Tools) не зависит от FastAPI и БД ([architecture.md](../architecture.md#компоненты)).
- Метод `run` у Tool синхронный ([tool-contract.md](../tool-contract.md#интерфейс)).

## Решение

1. `POST /runs` только создает Job, переводит его `created → queued` и сразу отвечает 201 с `id`. Состояние и результат клиент получает через `GET /runs/{id}`.
2. Очередь это сама таблица Job: Job в состоянии `queued` ждет выполнения. Отдельной очереди в памяти нет, поэтому `queued` переживает перезапуск.
3. Dispatcher работает в том же процессе, что и HTTP API. При старте приложения запускаются N рабочих потоков, N задается переменной окружения `WORKERS`, по умолчанию 2.
4. Свободный поток раз в секунду ищет самый старый Job в `queued` и переводит его в `running` одной атомарной операцией: условным `UPDATE` с проверкой текущего состояния. Поэтому два потока не возьмут один Job.
5. Отмена. API записывает `cancelled` через сервис Job. Tool узнает об этом через `context.is_cancelled()` в безопасной точке и останавливается. Результат, который пришел после отмены, Dispatcher отбрасывает.
6. Перезапуск. При старте, до запуска потоков, сервис переводит все Job в `running` в `failed` с кодом `internal_error` и сообщением «выполнение прервано перезапуском сервиса». Переход пишется в историю. Job в `queued` остаются и выполняются после старта. Прерванный Job повторно не запускается, потому что из `failed` переходов нет. Клиент создает новый Job.

Запуск потоков это код слоя приложения. Сам Dispatcher не знает, кто и сколько раз его вызывает, поэтому ядро по-прежнему тестируется без потоков: в тесте Dispatcher вызывают напрямую.

## Рассмотренные альтернативы

| Вариант | Плюсы | Почему не выбрали |
| --- | --- | --- |
| Синхронно, в обработчике `POST /runs` | Проще всего, результат сразу в ответе | Нет смысла в `queued` и в отмене `running`. Клиент ждет 30 с и дольше, а при обрыве не знает, создан ли Job |
| `BackgroundTasks` FastAPI или задачи asyncio в памяти | Почти ничего не нужно писать | Задача живет только в памяти: при перезапуске пропадают и `queued`, и `running` Job без следа. Привязывает выполнение к FastAPI |
| Отдельный процесс-воркер с той же таблицей Job | Тяжелые Job не мешают API, воркеры масштабируются процессами | Еще один сервис в Compose и еще одна точка отказа. Для нашей нагрузки пока лишнее. Это первый кандидат при пересмотре |
| Брокер: Celery или RQ и Redis | Готовые повторы, масштабирование, мониторинг | Еще два сервиса. Состояние Job пришлось бы держать и в брокере, и в БД. Для десятков Job в неделю это избыточно, брокеры не оцениваются |

## Цена решения

- Перезапуск сервиса прерывает Job, которые сейчас выполняются: они уходят в `failed`, клиент повторяет сам. Для Job длиной в секунды и минуты это приемлемо.
- Job стартует с задержкой до 1 с, а опрос дает лишние запросы к БД.
- Тяжелый разбор реплеев делит процессор с API, поэтому под нагрузкой API может отвечать медленнее.
- Сервис можно запускать только в одном экземпляре. Второй экземпляр при старте пометил бы `failed` Job, которые выполняет первый.
- SQLite плохо переносит параллельную запись, поэтому на прототипе `WORKERS=1`.

## Условия пересмотра

- Нужно больше одного экземпляра сервиса, или выполнение Job заметно замедляет ответы API. Тогда переходим на отдельный процесс-воркер, а прерванные Job находим по heartbeat, а не по факту перезапуска.
- `local_match` становится основным, и терять при перезапуске матчи по десятку минут дорого.
- Опрос раз в секунду заметно нагружает БД. Тогда заменяем его на `LISTEN/NOTIFY` PostgreSQL.
