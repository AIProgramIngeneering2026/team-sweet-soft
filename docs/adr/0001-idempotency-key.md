# ADR-0002. Защита от повторного POST /runs через Idempotency-Key

- Дата: 2026-11-14
- Статус: принято
- Автор: СавенкоДР
- Где в контракте: [openapi.yaml](../api/openapi.yaml), `POST /runs`, заголовок `Idempotency-Key`, ответы 200 и 409

## Контекст и ограничения

Клиент сервиса это скрипт или `curl` разработчика бота. `POST /runs` может прийти дважды: скрипт повторил запрос после таймаута, ответ потерялся в сети, человек запустил команду еще раз. Сервер не отличит такой повтор от нового задания с теми же параметрами, если клиент ему не подскажет.

Ограничения, от которых зависит решение:

- Повтор не должен создавать второй Job и запускать работу второй раз. Это критерий сценария 3 в [requirements.md](../requirements.md): повторный `POST /runs` с тем же ключом возвращает `id` того же Job, новая синхронизация с AI Arena не запускается.
- Одинаковые параметры отправляют повторно и намеренно. Повторный `arena_sync` через час должен создать новый Job и найти новые матчи (сценарий 3, второй критерий). Значит, искать повтор по содержимому запроса нельзя, нужен признак от клиента.
- Отклоненный запрос не занимает ключ. Если `POST /runs` с ключом получил 422 `unknown_tool`, повтор с тем же ключом и правильным именем создает Job (сценарий 4).
- Сервис это один процесс с одной БД: PostgreSQL, на прототипе SQLite. Пользователей и авторизации нет, клиент один.
- Создание Job короткое и синхронное: проверка, запись в БД, постановка в очередь. Долгая работа идет в фоне, поэтому ответ на `POST /runs` приходит быстро и состояния «запрос еще обрабатывается» у нас почти не бывает.

## Решение

1. `POST /runs` принимает необязательный заголовок `Idempotency-Key`: от 1 до 255 печатных ASCII символов, рекомендуем UUID v4. Клиент создает новый ключ на каждое новое задание и шлет тот же ключ при повторе. Остальные операции заголовок не принимают.
2. Ключ хранится в записи Job: колонка `idempotency_key` с уникальным индексом (`NULL` разрешен, Job без ключа не мешают друг другу) и колонка `request_hash`. `request_hash` это SHA-256 от `tool` и `params` в каноническом JSON: ключи отсортированы, без пробелов. Порядок полей в JSON на хеш не влияет.
3. Ключ записывается в той же транзакции, что и Job. Нет Job, нет и ключа: если запрос отклонен проверкой или упал до commit, ключ свободен.
4. Ответы:

   | Ситуация | Ответ |
   | --- | --- |
   | Ключа нет | Как обычно: 201, каждый запрос создает новый Job |
   | Ключ новый | 201, Job создан, ключ привязан к нему |
   | Ключ привязан к Job, `request_hash` тот же | 200, тот же Job в текущем состоянии, заголовок `Idempotent-Replayed: true`. Новый Job не создается, в очередь ничего не ставится, история не меняется |
   | Ключ привязан к Job, `request_hash` другой | 409 `idempotency_key_conflict`, в `message` id Job, к которому привязан ключ |
   | Ключ не по формату | 422 `invalid_params`, поле `header.Idempotency-Key` |

5. Порядок проверок: формат заголовка и тела, затем поиск ключа, затем Registry и `validate`. Повтор уже принятого запроса с тем же телом не проходит `validate` заново и получает 200, даже если правила проверки с тех пор поменялись.
6. Гонку двух одновременных запросов с одним ключом решает уникальный индекс. Второй `INSERT` ждет первую транзакцию и получает нарушение уникальности. Сервис читает Job, который успел записаться, и отвечает как на повтор: 200 или 409. Отдельных блокировок и состояния «ключ в обработке» нет.
7. Ключ живет, пока живет Job. Удаления Job сейчас нет, поэтому ключ занят навсегда.
8. Повтор возвращает текущее состояние Job, а не копию первого ответа. Клиент повторяет запрос, чтобы узнать `id`, а состояние все равно меняется: первый ответ мог быть `queued`, повтор может вернуть `running` или `done`.

Кто что делает (компоненты из [architecture.md](../architecture.md)): HTTP API проверяет формат заголовка, считает `request_hash` и выбирает код ответа. Сервис Job и хранилище атомарно создают Job вместе с ключом или возвращают Job, к которому ключ уже привязан. Про HTTP заголовки ядро не знает, оно получает ключ и хеш как обычные аргументы.

Что решение не покрывает:

- Клиент без ключа не защищен: два одинаковых запроса без ключа дадут два Job. Это сознательно, см. альтернативу «обязательный ключ».
- `POST /runs/{id}/cancel` ключ не принимает. Повторная отмена получает 409 `invalid_transition` (сценарий 6), фактическое состояние клиент смотрит в `GET /runs/{id}`. Отмена и так не создает новых сущностей, лишний повтор ничего не портит.

## Рассмотренные альтернативы

| Вариант | Почему не выбрали |
| --- | --- |
| Ничего не делать: клиент сам смотрит `GET /runs` перед повтором | Если ответ на `POST /runs` потерялся, клиент не знает `id` и не может надежно найти свой Job среди других. Между проверкой и повтором есть гонка |
| Искать повтор по содержимому: тот же `tool` и `params` за последние N минут дают тот же Job | Ломает намеренные повторы: второй `arena_sync` через час должен создать новый Job. Значение N не из чего выбрать, любое будет ошибаться в одну из сторон |
| Отдельная таблица ключей с сохраненным ответом и сроком жизни 24 часа, как в Stripe | Нужны отдельная таблица, фоновая чистка и хранение тела ответа. Нам достаточно связи «ключ → Job», а защищаемая операция одна. Запись в таблице Job дает ту же гарантию без новых частей |
| Обязательный ключ: без заголовка 422 | Простой вызов через `curl` перестает работать без генерации UUID. Лишний Job у нас дешевый: `arena_sync` не сохраняет дубли матчей (сценарий 3), `series_summary` только считает и не меняет данные. Неудобство для всех клиентов дороже редкого лишнего Job |
| Клиент сам задает id: `PUT /runs/{id}` | Меняет API, о котором уже договорились в README и сценариях. Клиенту все равно нужно генерировать уникальное значение, то есть это тот же ключ под другим именем, плюс новые ошибки «id занят» и «id не по формату» |
| 422 вместо 409 на тот же ключ с другим телом, как в черновике IETF `Idempotency-Key` | У нас 422 значит «исправь запрос», а здесь запрос сам по себе верный, он конфликтует с уже созданным Job. 409 уже означает конфликт с состоянием (`invalid_transition`), клиенту проще различать по коду ответа |

## Цена решения

- Две новые колонки и уникальный индекс в таблице Job, миграция Alembic.
- SHA-256 по `tool` и `params` на каждый `POST /runs` с ключом. У `series_summary` в теле лежат реплеи, до 100 МБ, хеш такого тела считается доли секунды. Канонический JSON требует разобрать тело целиком, но мы и так его разбираем.
- Ключ нельзя использовать повторно никогда. С UUID это не мешает, но клиент, который берет ключ из имени задания («sync-1234»), получит 409 при следующем запуске.
- Канонический JSON не сглаживает все различия: `1` и `1.0` или разный порядок реплеев в списке дают разный хеш и, значит, 409. Клиент должен повторять запрос байт в байт по смыслу, а не собирать его заново.
- Повтор отдает не копию первого ответа: статус может отличаться. Клиент должен опираться на `id` и `GET /runs/{id}`, а не на статус из ответа `POST /runs`.
- Защищен только `POST /runs`. Если появится еще одна операция, которая создает данные, для нее решение придется расширять.

## Условия пересмотра

- Появятся пользователи и авторизация. Ключ станет уникальным в пределах клиента (`client_id` + `idempotency_key`): иначе один клиент может занять ключ другого или по чужому ключу получить чужой Job.
- Появится удаление или архивирование Job. Нужно решить, освобождается ли ключ, или перейти на отдельную таблицу ключей со сроком жизни.
- Идемпотентность понадобится еще одной операции, например загрузке реплеев отдельным запросом. Тогда ключи переезжают в отдельную таблицу, общую для операций.
- Хранилище перестанет быть одной БД с транзакциями: несколько сервисов или очередь вне БД. Уникальный индекс перестанет закрывать гонку, нужен другой механизм.
- В логах будут видны лишние Job от клиентов без ключа, и они начнут мешать: делаем ключ обязательным.
