# ADR-0002. Защита от повторного POST /runs через Idempotency-Key

- Дата: 2026-11-14
- Статус: принято
- Контракт: [openapi.yaml](../api/openapi.yaml), `POST /runs`

## Контекст и ограничения

- `POST /runs` может прийти дважды: повтор после таймаута, потерянный ответ, повторный запуск скрипта.
- Повтор не должен создавать второй Job (сценарий 3).
- Те же параметры можно отправить намеренно: повторный `arena_sync` создает новый Job (сценарий 3). Искать повтор по содержимому нельзя.
- Отклоненный запрос не занимает ключ (сценарий 4).
- Один процесс, одна БД. Пользователей и авторизации нет.

## Решение

- `POST /runs` принимает необязательный заголовок `Idempotency-Key`, 1–255 печатных ASCII символов.
- В таблице Job две колонки: `idempotency_key` с уникальным индексом и `request_hash`, SHA-256 от `tool` и `params` в каноническом JSON.
- Ключ пишется в одной транзакции с Job. Запрос отклонен, значит ключ свободен.
- Ответы:

  | Ситуация | Ответ |
  | --- | --- |
  | Ключа нет | 201, новый Job |
  | Ключ новый | 201, новый Job |
  | Ключ есть, тело то же | 200, тот же Job в текущем состоянии, `Idempotent-Replayed: true` |
  | Ключ есть, тело другое | 409 `idempotency_key_conflict` |
  | Ключ не по формату | 422 `invalid_params`, поле `header.Idempotency-Key` |

- Одновременные запросы с одним ключом разводит уникальный индекс: второй `INSERT` падает, сервис отвечает 200 или 409.
- Ключ живет, пока живет Job.
- `POST /runs/{id}/cancel` ключ не принимает: повторная отмена дает 409 `invalid_transition`.

## Рассмотренные альтернативы

| Вариант | Почему нет |
| --- | --- |
| Ничего не делать, клиент проверяет `GET /runs` | При потерянном ответе клиент не знает `id` |
| Повтор по содержимому за N минут | Ломает намеренный повторный `arena_sync` |
| Отдельная таблица ключей с TTL | Лишняя таблица и чистка, операция одна |
| Обязательный ключ | Неудобно для `curl`, лишний Job у нас дешевый |
| `PUT /runs/{id}` с id от клиента | Меняет согласованный API |

## Цена решения

- Две колонки, индекс, миграция Alembic.
- SHA-256 тела на каждый запрос с ключом.
- Ключ нельзя использовать повторно.
- `1` и `1.0`, другой порядок реплеев дают другой хеш и 409.
- Клиент без ключа не защищен.

## Условия пересмотра

- Появится авторизация: ключ уникален в пределах клиента.
- Появится удаление Job: решить судьбу ключа или перейти на таблицу с TTL.
- Ключ понадобится другой операции: отдельная таблица ключей.
- Несколько сервисов или хранилище без транзакций: уникальный индекс не защитит.
- Лишние Job без ключа начнут мешать: ключ обязательный.
